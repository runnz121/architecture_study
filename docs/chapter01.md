# Chapter 1: You Have a New Project

## 챕터 요약

Video Tutorials 프로젝트를 전통적인 MVC CRUD 방식으로 구현하며, 이 방식의 근본적인 한계를 경험한다.
이후 이벤트 기반 마이크로서비스 아키텍처로 전환해야 하는 이유를 제시한다.

---

## 프로젝트: Video Tutorials

- **목표**: 차세대 인터넷 학습 플랫폼
- 콘텐츠 크리에이터가 영상 업로드, 사용자가 시청
- 첫 번째 요구사항: 글로벌 비디오 조회수 카운트

---

## MVC CRUD 구현

`videos` 테이블에 `view_count` 컬럼으로 조회수를 직접 관리한다.

```
videos
──────────────────────────────────────────
id | owner_id | name | description | transcoding_status | view_count
```

### API 엔드포인트
- `GET /api/home` → 전체 조회수 합계 반환
- `POST /api/record-viewing/{videoId}` → view_count + 1 증가

---

## MVC CRUD의 한계

| 문제 상황 | CRUD 방식의 한계 |
|---|---|
| 조회수 기반 크리에이터 정산 시 오류 발견 | 원본 데이터 없어 재계산 불가 |
| 시간별 시청 트렌드 분석 필요 | 데이터를 집계해버려 원본 소실 |
| `video_views` 테이블 추가 필요 | 과거 데이터 복구 불가 |
| 조회 검증(정당한 시청인지) 필요 | 동기 처리라 시간 초과 위험 |
| 다른 시스템에 "영상 시청됨" 알림 필요 | 범용 패턴 없이 일회성 해결책만 가능 |
| 조회 기록과 분석 로직 분리 | 단일 모델에 모든 관심사 결합 |

**결론**: MVC CRUD는 하나의 기능도 완성하기 전에 코너에 몰린다.

## 이벤트 기반 마이크로서비스 아키텍처 (해결책)

### 5가지 구성 요소

```
                    ┌─────────────┐
                    │ Applications │  ← 사용자 상호작용 (HTTP)
                    └──────┬──────┘
                           │ 메시지 쓰기
                    ┌──────▼──────┐
                    │ Message Store│  ← 중심 허브
                    └──┬───────┬──┘
              ┌────────▼──┐ ┌─▼────────┐
              │ Components │ │Aggregators│
              └────────┬──┘ └─┬────────┘
                       │      │
                    ┌──▼──────▼──┐
                    │  View Data  │  ← 읽기 전용 파생 데이터
                    └─────────────┘
```

| 구성 요소 | 역할 | 동작 모드 |
|---|---|---|
| **Applications** | 사용자 입력 처리, 화면 렌더링 | Request/Response |
| **Components** | 비즈니스 프로세스 수행 (자율적) | Batch |
| **Aggregators** | 상태 전이 → View Data 변환 | Batch |
| **View Data** | 읽기 전용 파생 데이터 (최종 일관성) | - |
| **Message Store** | 상태 전이 저장 + 메시지 전송 | 중앙 저장소 |

### 핵심 원칙

1. **상태 전이 저장** (Event Sourcing): 현재 상태만이 아니라 변경 이력 전체를 저장
2. **명시적 계약** (Explicit Contract): DB 공유가 아닌 메시지로 통신
3. **자율적 컴포넌트** (Autonomous): 단일 비즈니스 관심사를 캡슐화
4. **CQRS**: 쓰기(Message Store)와 읽기(View Data) 완전 분리

### CRUD vs Event Sourcing

```
CRUD:  UPDATE videos SET view_count = view_count + 1  (현재 상태만)
Event: INSERT { type: "VideoViewed", videoId, timestamp }  (변경 이력 보존)
```

---

## 아키텍처의 핵심 이점

| 원칙 | 이점 |
|---|---|
| 상태 전이 저장 (Event Sourcing) | 과거 데이터 재처리 가능, 감사 추적 자동 확보 |
| 명시적 메시지 계약 | 컴포넌트 간 결합도 제거, 독립 배포 가능 |
| 자율적 컴포넌트 | 인지 부하 감소, 장기 생산성 유지 |
| CQRS (읽기/쓰기 분리) | 읽기/쓰기 독립 최적화, 독립 스케일링 |

## CRUD 한계 체험 포인트

구현 후 스스로에게 던져볼 질문:

1. "조회수 계산 오류를 발견했을 때, 원본 데이터로 재계산할 수 있는가?" → **불가**
2. "특정 시간대의 시청 트렌드를 분석할 수 있는가?" → **불가**
3. "조회 기록 기능을 변경하면 홈페이지 표시에 영향이 있는가?" → **있음** (결합)
